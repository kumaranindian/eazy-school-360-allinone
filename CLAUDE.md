# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

EazySchool 360: a multi-tenant School Management SaaS (Web, Android, iOS) built with Flutter/Dart, Firebase (Auth, Firestore, Storage, Cloud Functions for push), Riverpod (no codegen) and GoRouter. The Dart package is `eazy_school_360`; the Android/iOS application id is `com.avail404.eazyschool.eazyschool360` (these are intentionally different — see `PROJECT_ARCHITECTURE.md`). Feature history is milestone-based (M0–M12); each milestone has a doc in `docs/milestone-*.md`. Prefer reading the relevant milestone doc before changing a feature.

## Commands

Flutter 3.32.8 / Dart 3.8 (pinned in CI).

```
flutter pub get
flutter run -t lib/main_dev.dart --dart-define=APP_ENV=dev -d chrome
flutter analyze                                   # must be clean
dart format --output=none --set-exit-if-changed . # CI enforces formatting
flutter test                                      # all unit + widget tests
flutter test test/path/to/file_test.dart          # single file
flutter test --plain-name "substring of test name"
flutter build web --release -t lib/main_prod.dart --dart-define=APP_ENV=prod
python3 tool/osv_scan_pub.py                      # dependency advisory scan (CI)
```

Firestore/Storage rules tests (separate Node project in `firestore-tests/`, run against emulators; Node 22, Java 21, `firebase-tools`):

```
cd firestore-tests && npm ci && cd ..
firebase emulators:exec --only firestore,storage --project demo-eazy-school-360 "cd firestore-tests && npm test"
# single file:
firebase emulators:exec --only firestore,storage --project demo-eazy-school-360 "cd firestore-tests && node --test staff-rules.test.mjs"
```

- `--project` must be exactly `demo-eazy-school-360` (hardcoded in the tests; `singleProjectMode` silently coerces everything else, making allow-tests fail while deny-tests still pass).
- Test files share one emulator and don't clear it: a new file must use its own school-id/uid prefixes. After an aborted run, kill stale `node --test` / emulator processes.
- `*-contract.test.mjs` replay JSON fixtures in `firestore-tests/fixtures/` that are **generated by Dart tests** (`test/*/..._write_contract_test.dart`). Run the Dart contract tests first (CI does) or the Node ones fail on stale/missing fixtures.

Cloud Functions (`functions/`, Node 22): `cd functions && npm install && npm test` (`node --test`). The deletion processor also has an emulator test: `firebase emulators:exec --only firestore,auth --project demo-eazy-school-360 "cd functions && node --test deletion_processor.emulator.test.js"`.

Rules build and repo tooling (`tool/`):

```
node --test "tool/*.test.js"          # tooling tests (manifest, signing, indexes, CSP, rules build…)
node tool/build_rules.js --check      # strip comments → build/rules/firestore.rules; fails over size budget
tool/deploy_rules.sh <project-id> --dry-run   # deploys the BUILT rules via firebase.rules.json
```

`firestore.rules` is the commented source and sits at the release-size limit (the release is refused with `Total size of compiled executables must be smaller than 256000 bytes` — on 2026-11-05 it was 38 bytes over; when it happens the CLI shows PATCH 400 then POST 409, so run `firebase deploy --debug` to see the real message; drop redundant `allow write: if false;` lines or add helpers); the deployed artifact is `build/rules/firestore.rules` (generated, never edited). Never `firebase deploy --only firestore:rules` with the default config. CI also reruns the whole rules suite against the built artifact (`RULES_FILE=../build/rules/firestore.rules STORAGE_RULES_FILE=../build/rules/storage.rules`).

Android release bundle (needs git-ignored `android/key.properties`, see `docs/android-release.md`; the build fails on purpose without it):

```
flutter build appbundle --release -t lib/main_prod.dart --dart-define=APP_ENV=prod \
  --dart-define=APP_CHECK_ENABLED=true --build-name=1.0.0 --build-number=<increasing int>
```

Diagnostic build flag: `--dart-define=AUTH_TRACE=true` makes `AppLogger.trace` print the sign-in/tenant/router flow in release builds (emails masked). Leave it off for production.

## Environments

Entry points are explicit: `lib/main_dev.dart`, `main_prod.dart` (optionally with a matching `--dart-define=APP_ENV=`), and `lib/main.dart`, which *requires* the define and has no default. Only `dev` and `prod` have real Firebase projects; `main_test.dart`/`main_uat.dart` hold placeholders and refuse to start. Per-env options live in `lib/core/config/firebase_options/`; see `docs/firebase-environment-configuration.md`. No `.firebaserc` is committed — pass `--project` to `firebase deploy`.

## Architecture

**Feature-first layering**: `lib/features/<feature>/{domain,data,presentation}`. Domain holds models, repository interfaces and *pure* rule classes (e.g. `TeacherAssignmentRules`, `AttendanceSavePlanner`, `ResultCalculator`, `HomeworkRules`, fee planners/reconcilers); `data/` holds `Firebase*Repository` implementations; presentation holds pages/widgets/Riverpod providers. Keep validation and business logic in the pure domain classes so they're unit-testable without Firestore. Widgets never touch `FirebaseFirestore.instance`/`FirebaseAuth.instance`/`FirebaseStorage.instance` — go through a repository provider. Cross-cutting infrastructure is in `lib/core` (config, routing, tenant, permissions, theme, errors) and shared UI in `lib/shared`.

**Multi-tenancy and authorization are enforced in Firestore rules, not the client.** Data is scoped `schools/{schoolId}/branches/{branchId}/...`; every tenant doc carries `schoolId` (and `branchId`) via `FirestoreFields` constants plus audit fields written with `FieldValue.serverTimestamp()`. `firestore.rules` and `storage.rules` use a lookup-table pattern against `/users/{uid}` (not custom claims). `TenantContext` (`lib/core/tenant`) is resolved from the signed-in user's profile and gates routing (no profile → `/create-school`; non-ACTIVE → `/account-inactive`). Roles/permissions live in `lib/core/permissions` (`UserRole`, `Permission`, `RolePermissions.grants`) — but that only controls UI visibility; any permission/role/collection change must be mirrored in `firestore.rules` **and** covered by a test in `firestore-tests/` (add both an allowed and a denied case). Step-by-step checklists: `MULTI_TENANT_GUIDE.md` ("How to add a new role", "How to add a new tenant-aware feature/collection"). Parent access is scoped by `linkedParentId` and class/section; see `docs/milestone-12a-blocker-closure.md` (F-SEC-3, "Refresh parent access" at cutover).

**Write paths are modeled as "write plans"** (`*Writes` classes such as `HomeworkWrites`, `ExamWrites`) so the exact documents the app writes can be exported as fixtures and replayed against the real rules in the contract tests. If you change what a repository writes, update the plan, rerun the Dart contract test, and rerun the rules tests.

**Login access**: `/users/{uid}.login` (server-written) + school `authSettings` gate sign-in per method; enforced in `firestore.rules`/`storage.rules` (`loginAllowed()`) and Cloud Functions (`functions/access.js`, `otp.js`, `whatsapp.js`). Phone OTP goes through Meta WhatsApp; see `docs/authentication-access-management.md` before touching auth. Admins give/reset logins for staff and parents (students sign in through parents) via the `provisionLogins` / `resetLoginPassword` callables with a per-batch `passwordSetup` option (name+mobile, random, activation email, reset link, admin-defined). The password is never stored or logged; options that set a password flag `users/{uid}.login.mustChangePassword`, which routes to `/change-password` (`changeInitialPassword` callable). That flag is enforced by the app and callable, not by rules. Bulk imports never create logins; they point to the staff/parents list.

**Platform admin** (Avail404 staff, `role: PLATFORM_ADMIN`, no school): a second factor (authenticator app) is required by every rule (`activeAndAllowed`/storage `loginAllowed`) and callable (`access.loginAllowed`); they live outside the school shell at `/platform` (`lib/features/platform_admin`), are created only by `tool/create_platform_admin.js` or the owner-only `createPlatformAdmin` callable (never by a client write), and every platform action writes `platformAuditLog`. Roles `OWNER/SUPPORT/COMPLIANCE/VIEWER` in `users.platformRole` (missing = legacy OWNER). Plan: `docs/platform-admin/PLATFORM_ADMIN_PLAN.md`; setup and deploy order: `docs/platform-admin/PLATFORM_ADMIN_RUNBOOK.md`.

**Account deletion** (Google Play requirement; `docs/account-deletion.md`, `docs/account-deletion-data-matrix.md`): requests come from Dashboard → Account → Delete account (`/delete-account`, `lib/features/account_deletion`) or a public web form in a separate repo. Every request is reviewed by a `PLATFORM_ADMIN` (`functions/account_deletion.js`, closed state table). `functions/deletion_processor.js` carries out approved requests and is **off** unless `ACCOUNT_DELETION_PROCESSING_ENABLED=true`; it has never run on real data. It never touches students or financial records. `functions/deletion_coverage.test.js` fails if any collection in `firestore.rules` has no deletion decision, so **a new collection also needs an entry in the deletion processor/matrix**. The UI never says "deleted" before the server reports `COMPLETED`.

**Multi-branch**: a school admin can act in any branch (`actsInAnyBranch`) and switches the acting branch from the header; upload/admission pages show `ActingBranchBanner` so it is clear where data lands (`docs/multi-branch.md`).

**Multi-country**: country, currency, time zone and date format are one setting per school (`schools/{id}`, edited in Settings → Regional settings; `docs/multi-country.md`). Money is integer minor units whose decimals depend on the currency (`Money.*` always takes the currency); "today"/deadlines/display use the school's zone via `SchoolTime` (`lib/core/regional`), never `DateTime.now()` for a school day; the currency locks once money exists (server-written `currencyLocked`).

**Notifications**: the app writes `broadcastNotices` / `notifications` docs; Cloud Functions in `functions/` fan these out to FCM (`docs/push-notifications.md`). Despite older text in `PROJECT_ARCHITECTURE.md` saying Cloud Functions weren't added, they now exist for push. Web push is not supported. Fee reminders are per-school policy (`schools/{s}/feeReminderSettings/config`, written only by the `updateFeeReminderSettings` callable; Settings → Fee reminders; days before/after the due date, delivery time, amount in text): see `docs/fee-reminders.md`. The Android small icon is a white logo silhouette (`res/drawable-*/ic_stat_notify.png`), regenerated from `assets/brand/logo_mark.png` if the logo changes.

**Tenant theme**: a school's colours are ONE configuration per tenant (`schools/{s}/branding/config`, written only by the `updateSchoolBranding` callable; platform default/presets in `platformBranding/default` via `updatePlatformBranding`), shared by every role and branch and updated live. `tenantThemeProvider` (`lib/features/branding`) feeds `AppTheme.light/dark(ResolvedTheme)`; pure rules (`BrandColors`, readability, `BrandingResolver`) are in `lib/core/branding`. Screens use `colorScheme`, `BrandTheme.of(context)` or `context.brandTone(legacyColor)` — never a tenant colour or raw hex; status colours (success/warning/error) are fixed. Signed out/between accounts shows the platform default. See `docs/tenant-theme.md`.

**Attachments** (announcements, homework): files live in Storage under the tenant path (`schools/{s}/branches/{b}/announcements/{id}/files/att_<id>.<ext>`); only metadata (`FileAttachment`) is stored in Firestore, never a download URL. Limits for type, size, count and file signature are in pure policy classes (`AnnouncementFilePolicy`) **and** independently in `storage.rules`/`firestore.rules`; change both together. Save order (`AnnouncementSaveFlow`): draft → upload → draft with metadata → delete removed objects → publish, with deterministic ids so retries never duplicate. See `docs/announcement-attachments.md`.

**Cloud Functions config**: `functions/.env.<project>` (copy `functions/env.example`, git-ignored) holds `FUNCTIONS_REGION=asia-south1`, WhatsApp settings, `ENFORCE_APP_CHECK` (keep false until apps send tokens) and `ACCOUNT_DELETION_PROCESSING_ENABLED`.

**Routing**: `go_router` with `StatefulShellRoute.indexedStack`; per-feature route files (e.g. `fees_routes.dart`) plug into `lib/core/routing`.

## Testing conventions

- Never hit real Firebase in Dart tests: override repository providers with fakes (`test/support/fakes.dart`, `staff_fakes.dart`, `attendance_fakes.dart`, …). `fake_cloud_firestore` is deliberately not used (incompatible with the pinned SDK's `meta`).
- Reading an auto-dispose `AsyncNotifierProvider`'s `.future` from a bare `ProviderContainer` needs a held `container.listen(...)` or the future hangs (see `test/core/tenant_context_provider_test.dart`).
- In status-driven widget tests, don't `pumpAndSettle` while a save spinner is shown; use `pump(duration)`.
- Theme: use `core/theme` tokens / `Theme.of(context)`, no raw colors or hex in feature code. Async state: `AsyncNotifier` + `AsyncValueWidget`, not ad hoc loading/error booleans.

## Shared UI building blocks (responsive layout)

List and hub pages share components in `lib/shared`; reuse them instead of hand-rolling dropdown rows and button walls:

- `filters/FilterBar` + `FilterField` — search and filters for list pages. Phones get a search box and a "Filters" button (bottom sheet, removable chips); wide screens show as many filters inline as fit. `fieldsBuilder` is called again after every change, so read live state (and provider values via `ref.read`) inside it. `FilterField.dropdown` treats a `null` option as "not filtered"; `countsAsFilter: false` is for context pickers (academic year); `FilterField.picker` is for dates. `searchController` is optional (filter-only pages).
- `filters/PageActionsMenu` — the "⋮" menu for secondary actions; keep one primary action (FAB or `SectionAction`).
- `layouts/StatChipsBar` — scrolling headline numbers that double as quick filters. Counts come from server-side `count()` aggregates (`countStaff`, `countStudents`), never from downloading documents.
- `layouts/SectionPage` — frame for sub-pages (title, back link, toolbar slot, primary action: header button on wide screens, FAB on phones). `SectionToolbar` / `ToolbarField` wrap pickers instead of overflowing.
- `layouts/ScopeBar` — controls that choose *what a page is about* (year/class/section/date); folds to a one-line summary on phones once complete.
- `layouts/HubGroup` / `HubTile` / `HubBadge` — grouped navigation tiles whose rows grow with the text size. `DetailGrid` — label-over-value read-only details.
- `layouts/ScrollableHeader` caps and scrolls a header that sits above an `Expanded` list. `ResponsiveDataList` takes `tabletColumns` to show fewer columns on tablets.
- The app clamps the system text scale at 1.5 and uses smaller headings on phones (`lib/app/app.dart`, `AppTypography.compact`). Don't give text containers a fixed height; size them from `MediaQuery.textScalerOf(context)` or let them grow.
- Layout tests (`test/widget/layout_responsive_test.dart`, `settings_*_test.dart`, `*_list_test.dart`) render at phone/tablet/desktop sizes and larger text scales and fail on any overflow; add one for new pages.
