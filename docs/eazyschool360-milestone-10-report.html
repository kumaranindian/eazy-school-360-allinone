Grading calculation and report card verification

  • One calculator (ResultCalculator) is the only place marks become percentages, grades and results; it is deterministic (same marks and scheme → identical result map, tested).
  • Zero, absent, exempted and pending are distinct; absent follows the scheme's policy; incomplete results cannot be finalised; GPA only with grade points; rank only when enabled.
  • Rounding is configured (decimals, half-up/down); the grade is looked up from the rounded percentage.
  • Report cards are generated from the stored, versioned result with its scheme and attendance snapshot (PDF built and checked for the %PDF header; content asserted at the result level). Printing and download use the existing printing package; there is no public URL.

Security and tenant verification

  • Tenant and branch isolation tested with direct reads/writes (School B admin, South branch admin/teacher, finance).
  • Only administrators configure, review, finalise, publish, withdraw, reopen and cancel; teachers and parents cannot, even with a correct history record.
  • Marks only by the ACTIVE assignment-slot teacher (or an administrator), for a student ACTIVE in that year/class/section, while marks entry is open and the sheet editable; bounds, absent/exempted semantics and component sums enforced.
  • Approver cannot be the submitter (school admin excepted); approval and return move the exam's counter in the same commit.
  • Results are create-only, version-matched, never updated or deleted; marks are frozen outside marks entry for everyone.
  • Parents read only a linked, portal-enabled, ACTIVE child's result, only while PUBLISHED and only the version in force; never marks, sheets, remarks, history or schemes.
  • Publication notice tied to the publish commit and unique per version; a retry cannot duplicate it.
  • Mutation check: 42 mutants, 40 killed, 2 equivalent (redundant by construction). Dart-written documents replayed through the real rules for the whole lifecycle including correction.

Limit: rules cannot recompute totals or count documents, so result figures and completeness counters are client-verified (single calculator, snapshot, history). A trusted backend would be required to make them tamper-proof. See docs/milestone-10-examinations-results-report-cards.md §9.

Bugs found by the tests and fixed

  • Calculator crashed for an entry with components but no stored total (effectiveMarks added).
  • A 'Result' tile overflowed on narrow screens (fixed-height tiles removed).
  • Subject dialog was empty when class subjects had not loaded (readAlive).
  • PDF used a dash glyph the built-in font lacks (ASCII-only text).
  • Rules: sheet changes were allowed after marks entry closed; any active user could update an examination; subject could be added without its counter; zero maximum accepted; principal remark could be written by a class teacher on first write; class of the student not checked — all found by the mutation check and fixed with tests.
  • Test helpers silently ignored mis-shaped overrides (caught by naming each expected denial).

Deployment prerequisites

  1. firebase deploy --only firestore:rules,firestore:indexes and wait for the indexes.
  2. Create a grading scheme, then examinations; teacher assignments must exist for marks entry.
  3. Run the rules suite serially with project id demo-eazy-school-360; regenerate the contract fixture with flutter test test/exams/exam_write_contract_test.dart after changing what the Dart code writes.

Unresolved issues

  • Rules cannot verify totals, grades or result completeness: results are calculated by the administrator's client (single calculator + stored scheme snapshot). A modified administrator client could write wrong figures or publish with results missing; a trusted backend would be needed.
  • A teacher of the branch can read any published result of the branch; any parent of the school can read a published examination's configuration. Results, marks and remarks of a child are link-protected.
  • Marks batches are five entries per commit (partial drafts possible, never a partial submission).
  • Families see the child's current class only; earlier classes are not looked up.
  • No student login, no separate approver role, no per-recipient notifications, no cross-examination term aggregates, no report card generation audit, Latin-1-only PDF text, no logo.
  • No end-to-end run against real Firebase; 5 new indexes unexercised; iOS build blocked by the environment.
  • Dashboards are partial (counts of loaded examinations, performance, family page).
