Security and tenant verification

  • Tenant and branch isolation tested with direct reads/writes (School B admin, South branch admin/teacher).
  • Only the ACTIVE assignment-slot teacher (or an admin on their behalf) creates/edits/publishes; other subjects, sections and invented subjects refused.
  • Submission only by a linked, portal-enabled, ACTIVE parent link of a PARENT account, for a child currently placed in that class+section and ACTIVE; ended link, portal off, and non-parent accounts refused.
  • Late status decided by the server clock; family cannot write marks, feedback or grader fields; graded work locked; moved/left child cannot resubmit.
  • Grades bounded by maxMarks, only by the homework's teacher or an admin, each with an append-only revision.
  • Announcement audiences: teachers only to their class-teacher SECTION, branch admins never ALL, parents/finance cannot create; audience immutable; archive not delete.
  • Notices tied to the event, revision, recipient and writer; forged and mismatched ones refused; no marks/feedback in notices.
  • Storage: create-only, type/size enforced, per-student paths need an ACTIVE portal link, draft files author/admin only.
  • Mutation check: 34 mutants, 32 killed, 2 equivalent (redundant by construction). Dart-written documents replayed through the real rules for every workflow.

Limit: rules cannot tie a parent to a section for reading, cannot hide a scheduled announcement, and Storage rules have a two-lookup budget; fan-out, reminders, cleanup and malware scanning need a trusted backend. See docs/milestone-9-homework-assignments-announcements.md §8.

Rules, indexes and schema

  • Collections (branch-scoped): homework, homeworkHistory, homeworkSubmissions, homeworkRevisions, announcements, announcementHistory, broadcastNotices; plus users/{uid}/noticeReads.
  • Notifications: targeted HOMEWORK_RETURNED / HOMEWORK_GRADED (existing collection, separate match); broadcast HOMEWORK_PUBLISHED / HOMEWORK_DUE_CHANGED / ANNOUNCEMENT_PUBLISHED / ANNOUNCEMENT_UPDATED.
  • Storage paths (create-only): homework/{id}/files, homework/{id}/submissions/{studentId}, announcements/{id}/files.
  • Indexes: +14 (75 total) — not exercised by the emulator.

Bugs found by the tests and fixed

  • Large update rules exceeded the 1000-expression budget (restructured with let-bound helpers and profile-based checks).
  • Teacher revision query had to pin the homework for the rules to prove access (query now pins it; tested both shapes).
  • File policy accepted exactly 10 MB while Storage requires < 10 MB (aligned).
  • A resubmission by a child who had moved sections would have been allowed (placement check added; mutation-checked).
  • A weak 'not their child' test ran after the document existed (reordered; mutant now killed).
  • Link-status, portal, role, author and revision-skip rules were initially untested (tests added; mutants killed).
  • Class-teacher announcement update exhausted the budget (restructured).

Deployment prerequisites

  1. firebase deploy --only firestore:rules,storage,firestore:indexes and wait for the indexes.
  2. Ensure teacher (and class-teacher) assignments exist.
  3. Run the rules suite serially with project id demo-eazy-school-360; regenerate the contract fixture with flutter test test/homework/homework_write_contract_test.dart after changing what the Dart code writes.

Unresolved issues

  • Parents are school-wide readers of PUBLISHED homework, announcements, notices and homework files; the app filters by child. Submissions/feedback are link-protected.
  • Scheduled announcements cannot be hidden before publishAt by rules; the app hides them.
  • Teacher file reads in Storage depend on createdBy; admin-created-on-behalf homework cannot be read by that teacher through Storage.
  • Submission uploads are not tied to deadline/enrolment in Storage (orphan objects possible); no cleanup, no malware scanning.
  • dueAt uses the publisher's local timezone; device clock skew near a deadline can show a submit that the server refuses.
  • No backend: no reminders, fan-out, scheduled publication or cleanup.
  • No end-to-end run against real Firebase; 14 new indexes unexercised; iOS build blocked by the environment.
  • The submission update rule uses ~70–85% of the evaluation budget; further conditions need offsetting.
  • Teacher dashboard and admin reporting are partial (see features); no bulk grading; no student login (project has none).
