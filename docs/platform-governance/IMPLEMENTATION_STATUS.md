## Phase 4 summary (2026-11-14)
**Implementation.** `functions/school_notifications.js`: one `platformNotifications/{sha(event|recipient)}` document per active SCHOOL_ADMIN for every lifecycle change (activated, reactivated, suspended, deactivated, expired, closed, recovered), created after the change commits and idempotent per change (a failure never undoes the change; the result reports `notified`). States CREATED -> DELIVERED (first listing by the recipient) -> ACKNOWLEDGED, or DISMISSED when no acknowledgement is required. Text: fixed copy plus the owner's optional message; the internal reason and internal notes are never copied. Callables `listMyPlatformNotifications`, `acknowledgeNotification`, `dismissNotification` always scope to the caller; someone else's id looks missing. A user paused by their school can still list (to read why).
**App.** `PlatformNotificationGate` in the shell: a pending notification opens a popup that cannot be dismissed (barrier and back disabled) until "I understand" is saved on the server (on failure it stays open with a message; it also returns next launch); oldest first. `PlatformMessagesButton` in the app bar opens the inbox with a pending count. School and branch admins only, never in a support session; polled every 2 minutes.
**Database/rules.** New collection `platformNotifications` with NO client rules (default deny), so the Firestore rules size is unchanged. Needs no index (single-field equality).
**Tests.** `school_notifications.test.js` (9), widget tests in `platform_availability_ui_test.dart` (popup, not dismissible, failure, order, roles, inbox, phone/large text), domain tests.

## Phases 7-8 summary (2026-11-14; decisions D6, D13 taken as recommended)
**Catalogue (Phase 7).** `functions/features.js` and its Dart mirror `lib/core/features/feature_catalogue.dart`: 16 real modules only (students, parents, staff, academic, attendance, leave, fees, feeReminders, admission, publicAdmission, exams, timetable, homework, announcements, messages, notifications), each with dependencies; no transport/library/payments. Effective switches stay in `schools.features` (the existing keys `admission`/`publicAdmission` are kept, D13); a missing key means ON, so every existing school is unchanged. Enabling needs every dependency on; disabling a module with dependants needs confirmation and switches them off too (nothing else). `setSchoolFeatures` (owner only): reason of 10+ characters when anything is switched off, one transaction of school + `schoolFeatureHistory` rows (one per key, cascade flagged, version) + audit, then an idempotent, dismissible notice to the school's administrators (never includes the internal reason). `platformFeatureDefaults/default` (owner-edited, must be consistent) is copied into each NEW school (server-created at creation; self-registered by the `schoolCreated` trigger), so a later default change never reaches an existing school. Callables `getFeatureConfig`, `setFeatureDefaults`, `getFeatureHistory`. Console: Modules panel on the school page (whole catalogue, dependency-aware switches, reason dialog listing what else goes off, history) and a "Default modules for new schools" dialog for owners on the Schools page.
**Enforcement (Phase 8).** (1) UI and routes: `TenantContext.can` maps every module permission to its module, so a switched-off module (or one whose dependency is off) loses navigation, routes and actions together; a test proves no permission is left unmapped (with every module off only the six module-free permissions remain). (2) Callables: the access engine's feature check is dependency-aware (`features.usable`) and used by the admin gateway, the admission wrapper, the fee-reminder settings callable and the scheduled reminders. (3) Rules: unchanged (no per-module clauses fit the size limit). (4) Detective trigger (D6): 18 `featureGuard_<collection>` triggers record a create in a disabled module's collection as `FEATURE_ACCESS_DENIED` (who, where, which module) in the platform audit log, one deterministic record per document. **They do not revert or delete anything**: automatically deleting a user's data is a destructive decision for you to make; the record lets the platform team act.
**Honest limits.** A modified client could still write to a disabled module's collection; it would be recorded, not blocked. Fully preventive enforcement for a direct-write module requires moving that module's writes to callables (a per-module project, not started). Reads of existing data in a disabled module are not blocked by the rules either (the UI hides them).
**Tests.** `features.test.js` (14), `feature_guard.test.js` (10), `index_exports.test.js` (loads index.js: it caught a use-before-define in `index.js` that no module test could), Flutter `feature_catalogue_test.dart` (catalogue integrity, permission mapping completeness, dependants), console widget tests (reason, cascade confirmation, dependency-disabled switches, roles, history, defaults), route tests (fees off refuses `/fees`; students off also refuses attendance but not homework; platform admins unaffected).
**Operational notes.** 18 new trigger functions fire on every create in those collections (one cheap read of the school document each): this is the D7 cost. Check the project's function-count quota before deploying. New collections `platformFeatureDefaults`, `schoolFeatureHistory` have no client rules; no new indexes. Functions first, then app. Do NOT deploy to production without approval.


## Phases 9-11 summary (2026-11-14; decisions D7-D9, D14 taken as recommended)
**Phase 9 - architecture.** `functions/audit.js` is the single trusted writer of `auditEvents/{yyyyMM}/events/{eventId}`: schema v1 validation (category, action, result, source and id formats), trust level derived from the source (never from the caller), deterministic event id (hash of source event + type; a retry is a no-op, `create` semantics, nothing is ever updated), server-derived time, month partitions. Redaction: forbidden keys (password, otp, token, secret, authorization, api key, download/signed URLs, credentials) are dropped at any depth, URLs carrying credentials become `[redacted-url]`, depth/size are bounded; changes carry values only for a per-entity allowlist and never for personal fields (phone, e-mail, address, DOB, guardian, medical, ids...). Reading is only through callables for platform OWNER and COMPLIANCE (MFA required): `queryAuditEvents` (filters: school, user, area, type, result, source, window of at most 92 days; newest first; cursor paging across months; page size 1-100; scan cap with a "truncated" flag; first page audited), `getAuditSummary`, `exportAuditEvents` (CSV, UTC, 10,000-row cap, spreadsheet-formula neutralised, the export itself audited, the record holds no exported content). `reportClientEvent` (any signed-in user): allowlisted types only, identity from the token, stored as untrusted T4, 20 per 10 minutes per user. `auditRetention` (daily): exports months older than 400 days to Cloud Storage as JSON lines with a checksum marker; **deletes nothing unless `AUDIT_RETENTION_DELETE=true`** and only after reading the archive back. Six composite indexes (`events`: school, user, area, type, result, source + time).
**Phase 10 - instrumentation.** `moduleWatch_<collection>` (20 triggers; they replace the 18 `featureGuard_*` triggers, so the function count did not grow with auditing) record every create/update/delete of the client-written modules with the actor the rules guarantee; `auditMirrorPlatform` and `auditMirrorAuth` copy the existing platform and sign-in trails into the central one. The coverage matrix (`AUDIT_EVENT_COVERAGE.md`) lists what is Done, what is not built and what cannot be captured; it is deliberately blunt about gaps.
**Phase 11 - dashboards.** Console page "Audit trail" (owner and compliance only): 24-hour headline numbers (total, denied, failures, reported by the app), presets (Everything, Security, Denied, Failures, Reported by the app), window / area / school / user filters, newest-first list with result and "reported by the app" badges, detail dialog (who, role, app, school, target, summary, changes, a plain-language trust line), load more, "wide search" warning, CSV copy. A school's own administrators do not see the trail (D14: default off).
**Tests.** `audit.test.js` (27: schema, trust, ids, redaction, change allowlists, idempotent writer, mirrors, module diffs, permissions, ordering, filters, windows, paging without gaps or duplicates, audited reads/exports, CSV safety, summary, T4 rate limit and identity, retention archive/verify/delete), `index_exports.test.js` (loads `index.js`), Flutter `platform_audit_trail_test.dart` (30: roles, summary, list, badges, detail, presets, filters, paging, truncation, errors, export, phone/tablet/desktop at large text, filter and view models). The Firestore fake now supports ordered queries and cursors.
**Cost / operations.** Each write in a watched collection costs one trigger invocation and one audit write (D7). Attendance marks are excluded for that reason. Retention only writes to Cloud Storage; check the bucket and its lifecycle before enabling deletion, and confirm retention with your legal advisor (D9). Deploy order: indexes (they take time to build) and functions first, then the app. No rules change. Do NOT deploy to production without approval.
**Not done.** The app does not send T4 reports yet; LOGIN_SUCCESS needs Identity Platform blocking functions (approval); several areas are not yet in the central trail (see Known gaps).
