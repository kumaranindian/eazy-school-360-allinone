# Deployment checklist (repeatable)

Use for staging first, then production. Tick only with recorded evidence (command output / screenshot reference). **Never run these against production from an audit session.**

## A. Pre-release (T-3 days)
- [ ] `main` green: `dart format --output=none --set-exit-if-changed .`, `flutter analyze`, `flutter test`, `cd functions && npm test`, rules suite (`firebase emulators:exec --only firestore,storage --project demo-eazy-school-360 "cd firestore-tests && npm test"`), OSV scan (`python3 tool/osv_scan_pub.py`) and `npm audit --omit=dev` reviewed
- [ ] Contract fixtures regenerated by Dart tests before the rules suite
- [ ] `wc -c firestore.rules` < 200,000 and `firebase deploy --only firestore:rules --dry-run --project <p>` succeeds
- [ ] New query shapes have composite indexes deployed **and Enabled** (console)
- [ ] Release notes list rules/index/function/app changes and the mixed-version risk (deploy the **app first** when the rules tighten what old builds do — e.g. standalone academic years)
- [ ] Secrets present (names only): `META_WA_ACCESS_TOKEN`, `OTP_PEPPER`; `functions/.env.<project>` reviewed; `FCM_VAPID_KEY`, `APP_CHECK_WEB_KEY` supplied to the build
- [ ] Android: `android/key.properties` + upload keystore (backed up); iOS: distribution cert/profile, APNs key uploaded
- [ ] Backup: PITR enabled; a backup/clone taken **now**; last restore drill < 90 days

## B. Release order
1. Indexes (wait until Enabled) → 2. Functions (`firebase deploy --only functions`) → 3. Back-fill jobs where needed (`Refresh teacher access` per branch, `Refresh parent access` per branch) → 4. Rules/Storage rules → 5. Hosting build `flutter build web --release -t lib/main_prod.dart --dart-define=APP_ENV=prod --dart-define=FCM_VAPID_KEY=… --dart-define=APP_CHECK_ENABLED=true --dart-define=APP_CHECK_WEB_KEY=…` → 6. Mobile builds (`flutter build appbundle` / `ipa`, signed) → 7. only then `ENFORCE_APP_CHECK=true`
- [ ] Each step's output saved; versions/commit hash recorded

## C. Smoke test (staging, then production canary school)
- [ ] Sign in as school admin, branch admin, finance, teacher, parent (email, Google, OTP if enabled); sign out; sign in as another user on the same device
- [ ] Cross-tenant: user of school B cannot open school A's student/fee/notice (expect permission-denied)
- [ ] Parent sees only own children; teacher only assigned sections
- [ ] Create student → guardian link → portal login; duplicate admission number is refused
- [ ] Mark attendance on a date; apply and approve leave **on the last day of the academic year**
- [ ] Marks → submit → approve → finalise → publish → parent sees result
- [ ] Generate one invoice; collect a part payment twice quickly (one payment recorded); reverse it; check balance & audit entry
- [ ] Push: foreground/background/terminated on Android, iOS, web; sign out → no further pushes to that device
- [ ] Crash test event appears in Crashlytics (Android + iOS release builds)
- [ ] Deep link + browser refresh lands on the same page

## D. Rollback
- Rules: redeploy the previous ruleset (`git show <sha>:firestore.rules`), verify with smoke test A/C
- Functions: redeploy previous commit; set `ENFORCE_APP_CHECK=false` and redeploy if clients are being rejected
- Hosting: roll back to the previous release in the Hosting console
- Mobile: halt staged rollout; users stay on the previous build
- Data: do **not** restore over the live database; clone/restore to a new database, verify counts and `InvoiceReconciler`, then copy back affected collections with an audited script

## E. Post-release (T+1 h, T+1 day, T+1 week)
- [ ] Functions error rate, push delivery statuses (`pushDeliveries` FAILED/PARTIAL), auth anomalies, billing/quotas
- [ ] Crash-free sessions, top crashes triaged
- [ ] Firestore read/write volume vs. forecast; no `failed-precondition` (missing index) in logs
- [ ] Support channel monitored; incident contact list current
