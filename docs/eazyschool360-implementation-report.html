What was actually wrong (before this audit's fixes)

The single most important finding: a brand-new, unprivileged account could create its own /users/{uid} profile claiming role: SCHOOL_ADMIN of any existing school — including one it had no relationship to — because the self-signup rule checked only "does this account already have a profile," not "is this school actually new." This is a full tenant-takeover path and is now closed (see Finding SEC-01 in §15). The underlying design doc's reasoning for why this used to require a non-atomic two-phase write was also factually wrong (Firestore rules' getAfter()/existsAfter() do see same-batch writes) — correcting that understanding is what made the real fix (one atomic batch, cross-validated) possible.

  • Architecture: clean feature-first layering, no god classes/widgets found, no direct Firestore calls from widgets, no hard-coded role checks in UI code (verified by grep across lib/features/*/presentation and lib/core/routing — zero matches).

07 Multi-Tenant Architecture

Where tenant identity actually comes from (traced, not assumed)

  • schoolId / branchId: read from the signed-in user's own /users/{uid} Firestore document — never from a client-supplied parameter, local variable, or widget argument. Confirmed by reading TenantContextNotifier.build(): it derives everything from authState.uid and the fetched profile.
  • Current user: held in TenantContext.user, assembled once per sign-in by tenantContextProvider, read everywhere via ref.watch(tenantContextProvider) — not duplicated into separate ad hoc state.
  • Centralization: YES. Exactly one provider (tenantContextProvider) is the source of tenant context; grep confirms no other file independently re-derives schoolId.
  • Can the UI override schoolId? NO for reads (always the caller's own profile). For writes, repository methods do accept a schoolId parameter (e.g. getBranch(schoolId, branchId)) — this is necessary for an admin acting on their own school, and is safe only because Firestore rules independently re-derive and check the caller's real schoolId via get() on every write, never trusting the parameter alone.
  • Is tenant information trusted from the client? NO — see §10. Every rule that matters re-derives the caller's role/schoolId/branchId server-side from their own profile document, which only privileged writers (not the user themself, for the authorization fields) can change.

Dangerous-pattern search

Searched for .where('schoolId' or equivalent client-side-trust query patterns: NONE FOUND (grep -rn "\.where(" lib → no matches; no feature queries a collection by a client-supplied tenant filter yet, since no business collections exist). This is the correct state for this milestone — the risk this pattern represents is a future concern for whoever builds the first business feature, and is called out as such in MULTI_TENANT_GUIDE.md → "How to add a new tenant-aware feature."

Tenant model

Platform (PLATFORM_ADMIN — not scoped to any school)
↓
School /schools/{schoolId} (SCHOOL_ADMIN — scoped to this school, all its branches)
↓
Branch /schools/{schoolId}/branches/{branchId} (BRANCH_ADMIN / TEACHER / FINANCE / PARENT)

Why /users is a flat collection, not nested under /schools/{schoolId}

Verified rationale in FIRESTORE_ARCHITECTURE.md and confirmed consistent with the actual rule/schema: a client must be able to answer "what school am I?" before it knows any schoolId to construct a nested path — a flat /users/{uid}, self-readable by its own owner, is what makes that bootstrapping possible. This is a sound, deliberate design choice, not an oversight.

10 Firestore Security Rules

Full line-by-line review of firestore.rules (the post-fix version). No allow read, write: if true or equivalent exists anywhere — confirmed by direct inspection, not a keyword search alone.

Authentication requirement

Every rule gates on isSignedIn() (request.auth != null) at minimum. The bottom fallback (match /{document=**} { allow read, write: if false; }) denies anything not explicitly matched, including for signed-in users — confirmed by test ("an unmatched collection path default-denies even a signed-in, profiled caller").

User-profile / status validation

isActiveCaller() requires both a profile to exist and status == 'ACTIVE'. An INVITED or DISABLED caller fails every isActiveCaller()-gated check — the only thing such an account can still do is read its own /users/{uid} document (so the client can show why it's blocked). Verified for both statuses by test.

Tenant (school/branch) isolation

Enforced via a lookup-table pattern: every authorization decision reads the caller's own profile via get(), never trusting the request's own claimed schoolId for who the caller is. isSameSchool/isSchoolAdminOf/isBranchAdminOf all compare the caller's looked-up schoolId/branchId against the target. Demonstrated by 6+ dedicated isolation tests (School A vs. B, branch-level, cross-school create/update attempts).

Create / Read / Update / Delete permissions

CollectionCreateReadUpdateDelete
/users/{uid}Self-signup (atomic batch only) OR same-school/branch admin provisioning a subordinate, role-restrictedSelf, same-school admin, same-branch branch-admin, platform adminSelf (profile fields only) OR scoped admin (role/status/branch, never to admin roles) OR platform adminif false — soft-delete via status only
/schools/{id}Self-signup atomic batch onlySame school or platform adminSchool admin (profile fields, not status) or platform adminif false
/schools/{id}/branches/{id}School/platform admin, or main inside self-signup batchSame school or platform adminSchool admin (any field set) or that branch's admin (non-status fields)if false

Role validation & privilege-escalation resistance

  • No path lets a client-supplied write set role: 'PLATFORM_ADMIN' — verified absent in every create/update branch.
  • A SCHOOL_ADMIN can never be created/edited by another SCHOOL_ADMIN (admins only manage roles listed in schoolAdminManagedRoles(), which excludes SCHOOL_ADMIN itself).
  • A new account can only become SCHOOL_ADMIN of a school it is simultaneously creating in the same batch (post-fix) — never an existing one.

Client-controlled vs. immutable fields

  • Immutable on update, for everyone: createdAt, createdBy (validUpdateAudit()).
  • Server-enforced, not client-chosen (fixed this audit, SEC-04): createdAt/updatedAt must equal request.time; createdBy/updatedBy must equal request.auth.uid.
  • Field-scoped updates: every update rule uses request.resource.data.diff(resource.data).affectedKeys().hasOnly([...]) to enumerate exactly which fields a given actor may touch — not just "which values are acceptable," closing the SEC-03 hole where an allowed actor could change an unrelated field (like status) alongside a permitted one.
No secrets of any kind appear in firestore.rules or storage.rules — both are pure authorization logic with zero embedded credentials, confirmed by direct reading.

11 School Creation Flow

Actual implementation in FirebaseSchoolRepository.createSchoolForCurrentUser, post-fix.

ONE atomic WriteBatch:
↓
Create School
+
Create School Admin user profile
+
Create Default Branch ("main")
↓
batch.commit() — all three exist, or none do

Failure-scenario analysis

What happens if school creation succeeds but admin-profile creation fails? It cannot — both are part of the same WriteBatch, which Firestore commits atomically; there is no window where one exists without the other. This was not true before this audit's fix: the original implementation used two separate writes (a batch for school+profile, then a separate call for the branch), justified by an incorrect belief that Firestore rules cannot see same-batch writes. That belief was wrong (getAfter()/existsAfter() exist specifically for this), and the two-phase design is what left the SEC-01 hole open — rules couldn't easily verify "this profile belongs to a school really being created right now," so the self-signup rule fell back to the weaker (exploitable) check "the account just doesn't have a profile yet."

Idempotent repair path (for accounts created under the old flow)

If an account has a profile but — because it predates this fix — no default branch, calling createSchoolForCurrentUser again detects the existing profile and creates only the missing branch (now a legitimate write, since the caller is by then an active SCHOOL_ADMIN of that school). This repair path is real code, covered implicitly by the repository's existing-profile branch, though not currently exercised by an automated test (see §16 recommendations).

15 Security Audit

Every finding below was reproduced as a failing test against the pre-fix rules before being fixed, then re-verified passing after the fix — this is evidence-based, not a code-reading guess.

SEC-01 — Self-signup could claim an existing school as SCHOOL_ADMINCRITICAL
Location: firestore.rules (/users create rule, pre-fix) · Status: FIXED

A brand-new account (no existing profile) could set its own /users/{uid} document with schoolId pointing at any school already in the database and role: 'SCHOOL_ADMIN'. The only check was "does this uid already have a profile" — it never verified the school was new or that the caller had any real relationship to it. This is a full tenant takeover: an attacker who merely knows (or guesses) a schoolId becomes that school's admin.

Impact: complete compromise of an arbitrary existing tenant's data.

Fix: self-signup now requires creating the school and the profile in one atomic batch; the rule uses getAfter()/existsAfter() to confirm the referenced school did not exist before this write and was authored by the same caller in the same batch.

Reproduced by: test('ATTACK: a fresh account cannot self-claim SCHOOL_ADMIN of an EXISTING school') — failed before the fix, passes after.

SEC-02 — Orphan-tenant profile creationHIGH
Location: firestore.rules (/users create rule, pre-fix) · Status: FIXED

A new account could create a SCHOOL_ADMIN profile referencing a schoolId that was never created at all (no matching /schools/{id} document ever existed). Lower severity than SEC-01 (no real tenant is compromised), but still a data-integrity and authorization-logic defect — the same root cause.

Fix: same isSelfSignupBatchFor() fix as SEC-01.

test('ATTACK: a fresh account cannot create a profile pointing at a school it never created')

SEC-03 — School admin could self-reverse a platform-level suspensionHIGH
Location: firestore.rules (/schools update rule, pre-fix) · Status: FIXED

The update rule allowed a SCHOOL_ADMIN to update "their own school" without restricting which fields. Since status (ACTIVE/INACTIVE/SUSPENDED) is a field on the same document, an admin could rewrite it — undermining any future platform-level suspension/moderation capability.

Fix: school-admin updates restricted to profile fields only (name, logoUrl, email, phone, address, city, state, country) via diff().affectedKeys().hasOnly([...]); status changes require isPlatformAdmin().

test('a school admin cannot change their own school status (e.g. lift a platform suspension)')

SEC-04 — Audit fields were client-controlledHIGH
Location: firestore.rules (all create/update rules, pre-fix) · Status: FIXED

Rules checked that createdAt/createdBy didn't change on update, but nothing verified they were set correctly on create — a client could set createdAt to an arbitrary backdated timestamp or createdBy/updatedBy to impersonate a different user, undermining every audit trail in the system.

Fix: validCreateAudit()/validUpdateAudit() now require createdAt == request.time, updatedAt == request.time, and the actor fields to equal request.auth.uid.

test('audit fields cannot be forged on create or update') — covers both a backdated timestamp and an impersonated updatedBy.

AUTH-01 — INVITED accounts were not blocked from reaching the dashboardMEDIUM
Location: lib/core/tenant/tenant_context_provider.dart (pre-fix) · Status: FIXED

The client-side check only tested status == UserStatus.disabled. An INVITED (not-yet-activated) profile would fall through that check, load a full TenantContext, and reach the authenticated dashboard — even though firestore.rules already denied such a caller real data access (so the UI would show a dashboard that then fails on every read). Client/server disagreement on what "active" means.

Fix: check widened to status != UserStatus.active; exception generalized to AccountInactiveException(status) with status-aware messaging on a new /account-inactive page.

testWidgets('signed in, INVITED profile -> account-inactive page (not a splash retry loop)')

ARCH-01 — Route permission enforcement and nav-item visibility could silently drift apartMEDIUM
Location: lib/core/routing/app_router.dart, app_shell.dart (pre-fix) · Status: FIXED

The router's redirect logic did not check permissions for already-resolved tenants at all (any signed-in, active user could navigate to /school or /users by typing the URL, even if their role lacked the permission) — the nav shell simply didn't show the link, which is a usability nicety, not an access control, per this project's own stated security principle.

Fix: added AppRoutes.requiredPermissions, a single map both the router's redirect and AppShell's nav filter now read from, closing the direct-URL bypass and eliminating the drift risk.

testWidgets('parent cannot open /school by URL — redirected to dashboard'), testWidgets('teacher cannot open /school but can open /users'). Mutation-tested (guard disabled → 7 tests failed → guard restored → all pass).
